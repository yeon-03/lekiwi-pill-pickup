# LeKiwi 약통 집기 프로젝트 — 세션 인수인계 문서 (2026-08-27)

이 문서는 새 Claude 세션이 이 프로젝트를 이어받을 때, 오늘 하루(그리고 그 이전 세션)
동안 있었던 모든 로직·결정·버그·미해결 문제를 빠짐없이 파악할 수 있도록 쓴 것이다.
**로봇은 위험하니, 실제로 움직이는 명령을 내리기 전에 반드시 이 문서를 끝까지 읽을 것.**

## 0. 지금 당장 확인할 것

- 작업 디렉터리: `~/lekiwi-pill-pickup` (git 저장소, **오늘 작업 전부 미커밋 상태**)
- 로봇: LeKiwi(전방향 3바퀴 베이스 + SO-101 팔), 파이 IP `192.168.0.201`
  (⚠️ DHCP라 바뀔 수 있음 — `lekiwi.sh`가 자동 탐색하도록 되어 있음, 5번 항목 참고)
- 판(보드)에 병 3개가 좌(빨강)·중(초록)·우(파랑) 순서로 고정 간격으로 걸려 있음
- 카메라 2대: **베이스캠**(front, 로봇에 붙어 있음, `/dev/shm/lekiwi_cam/front.jpg`) +
  **고정캠**(fixed, 로봇 밖에 위에서 내려다봄, `/dev/shm/lekiwi_cam/fixed.jpg`)

  단 한 번도 성공 못 했다(정렬은 매번 훌륭했는데 하강이 항상 같은 지점에서 막힘).
  파랑(blue)은 오늘 단 한 번도 시도조차 안 함.**

## 1. 시작하는 법

```bash
cd ~/lekiwi-pill-pickup
./scripts/lekiwi.sh up              # 파이 호스트+고정캠서버+로봇브릿지+뷰어까지 자동 기동
./scripts/lekiwi.sh status          # 지금 상태(병 개수, 마커 유무, 정렬 오차) 확인
./scripts/lekiwi.sh home            # 팔 홈으로
./scripts/lekiwi.sh pick green      # 초록 집기 전체 사이클(추천 시작점 — 유일하게 되는 것)
./scripts/lekiwi.sh pick red --grasp-lift 68   # 빨강(아직 성공 못 함)
./scripts/lekiwi.sh align red       # 하강 직전에 멈춤(시차보정/디버깅용)
./scripts/lekiwi.sh grasp red       # align으로 멈춘 자세에서 하강만 이어서
./scripts/lekiwi.sh down            # 전부 종료
```

**매 사이클 전에 반드시**: `home` → 병 3개 위치 확인(`find_bottles_on_board`) → 시도.
사이클이 실패하면 병이 넘어지거나 밀렸을 수 있으니 반드시 재확인 후 다음 사이클 진행.

## 3. 물리적 좌표계/부호 — 절대 헷갈리면 안 되는 것

- **LeKiwi는 오도메트리/헤딩센서가 없다.** "+x=전진"이 항상 참인지 보장 안 됨 —
  실측(`calibrate_base_signs.py`)으로만 확정할 수 있음.
- **베이스캠은 로봇 몸체에 고정**되어 있다 → 화면의 왼쪽은 헤딩과 무관하게 항상
  "로봇의 왼쪽"이다. 그래서 베이스캠 기준 제어(`approach_board.py`)는 테스트 펄스 없이
  `base_nudge.py` 규약을 그대로 믿고 쓸 수 있다.
- **고정캠은 로봇 밖에 있다** → 헤딩을 모르면 화면의 좌우가 로봇의 좌우와 어떻게
  대응하는지 알 수 없다. `align_and_grasp.py`/`move_marker_to_bottle`은 그래서 매번
  작은 테스트 펄스로 방향을 실측한다(`calibrate_direction_matrix`, 또는
  `move_marker_to_bottle` 내부의 1회성 방향 프로브).
- **실측 확정된 부호** (`config/base_signs.json`, `calibrate_base_signs.py`로 구함):
  - `theta_to_reduce_mid_off = -1.0`
  - `y_to_grow_left = +1.0`
  - `x_forward = +1.0`
  - **중요한 교훈**: 처음엔 "부호가 이상하다"고 의심해서 "오차가 커지면 그 자리에서
    부호를 뒤집는 자기교정" 로직을 넣었었는데, **그게 하루를 통째로 날린 원인이었다.**
    실측해보니 `base_nudge.py`의 원래 규약이 처음부터 다 맞았다. 자기교정 로직은
    완전히 제거됨. **다시는 "부호가 이상해 보인다"고 자기교정을 넣지 말고, 반드시
    `calibrate_base_signs.py`로 재측정할 것.**
- **화면 x 방향과 로봇 물리적 좌우 방향의 관계(고정캠 기준, 실측)**:
  `vy=-0.05`(로봇 물리적 오른쪽) → 화면 x **감소**.
  `vy=+0.05`(로봇 물리적 왼쪽) → 화면 x **증가**.
  즉 "로봇을 더 오른쪽으로"는 "화면 x를 더 줄이는" 것과 같다.

## 4. 베이스캠 정렬 로직 (`approach_board.py`의 `align_base`) — 우선순위 4단계

사용자가 정의한 절차(2026-08-26/27 확정):

1. **병이 3개 미만 또는 너무 가까움(옆/가운데 비율 붕괴)** → 후진만. 단, 2개만 보이는데
   무리가 화면 한쪽 끝에 쏠려 있으면 "거리 문제"가 아니라 "안 보이는 병이 그쪽에
   있는 것"이므로 후진 대신 그쪽으로 회전(`ROTATE_FIRST_PX=60`).
2. **좌우 박스 크기 균형(게걸음)** — **회전보다 먼저 해야 한다.** 이유: 회전은
   좌우폭 비율에 거의 안 흔들리는데(실측: 회전 후 균형 변화 -0.6%p), 가운데 박스
   위치는 회전과 평행이동 둘 다에 흔들린다. 그래서 안 흔들리는 쪽(균형)을 먼저
   확정해야 회전이 그걸 다시 안 깬다. **순서를 반대로 하면 무한 진동한다** —
   실제로 되돌리기 작업 중 실수로 순서가 뒤집혔던 적이 있었고, docstring과 실제
   코드 순서가 어긋나 있는 걸로 발견해서 다시 바로잡았다. **이 순서는 절대 건드리지
   말 것.**
3. **가운데 병 중앙 정렬(회전)**.
4. **좌우 끝에 딱 붙을 때까지 전진.**

`at_base_position()` = 위 4조건(3개 다 보임, 균형, 가운데 정렬, 여백)을 전부 만족.
**간격(좌우 박스 중심 간격이 고른가)은 사용자가 제안한 좋은 아이디어지만, 제어에는
안 쓰고 진단 로그로만 남긴다** — 실측해보니 회전 신호로 쓰기엔 너무 약하고(±2%p
수준), 오히려 폭균형(±12.7%p)이 훨씬 강한 신호였다. 성공했던 위치의 간격차가
+17%였던 적도 있어서, "간격이 고르다=완료"로 쓰면 성공을 오히려 막을 뻔했다.

### 4-1. 오늘 발견하고 고친 진짜 버그들 (전부 실측 기반, 시간순)

1. **베이스캠 180도 뒤집힘**: 카메라가 거꾸로 달려서 화면 왼쪽=로봇 오른쪽이었다.
   `robot_bridge.py`의 `_publish_frame`에서 `CAMERA_ROTATE_180`으로 회전 처리.
2. **자기교정 부호 로직이 근본 원인**: 위 3번 항목 참고. 실측(`calibrate_base_signs.py`)
   으로 확정 후 자기교정 코드 전부 제거, `SIGNS` 딕셔너리를 파일에서 로드만 함.
3. **최소 펄스가 허용오차보다 큰 목표를 세웠던 버그(2건)**:
   - `move_marker_to_bottle`의 `MARKER_MOVE_TOL_PX=6`(고정값)이 미세모드 최소이동량
     (10.7px)보다 작아서 **원리적으로 수렴 불가능**한 상태로 방치돼 있었다(로그:
     144→206→148로 무한왕복). → `_achievable_tol()`로 **실측 이동량 기준 자동 계산**
     하도록 변경(항상 이동량보다 15% 여유 있게). `MARKER_MOVE_TOL_MIN_PX=6`은 하한선일 뿐.
   - `align_base`의 회전/균형 단계도 같은 클래스 문제가 있었으나(오차 크기만 보고
     속도를 낮추는 "미세모드"), **거리(여백이 0에 가까움) 자체가 민감도를 극단적으로
     높이는 경우**엔 오차 크기와 무관하게 항상 느려야 한다는 걸 나중에 또 발견함
     (아래 6번).
4. **"오차가 줄었을 때만 학습" 버그**: 게걸음/회전의 실측 이동속도(`bal_per_sec`,
   `mid_per_sec`)를 "오차가 줄어든 경우에만" 기록했는데, 매번 오차를 넘어가버리면
   영원히 학습을 못 해서 계속 같은 크기로 재넘어간다. → **부호와 무관한 절대
   이동량**으로 학습하도록 수정(한 번에 배움).
5. **`too_far()`가 "둘 다"가 아니라 "둘 중 하나"만 크면 됐던 버그**: 한쪽만 여백이
   크고 한쪽은 이미 붙어있어도 전진을 멈춰서 "여백 19/36"에서 완료 처리해버렸다.
   → `max(left_gap, right_gap) > EDGE_MARGIN_PX`로 수정(둘 다 붙어야 함).
6. **균형/회전이 "완전히 붙은 거리(여백 0)"에서 서로를 부수는 결합 문제**: 균형을
   -16%까지 잘 맞춰도 다음 회전 한 번에 -79%로 부서지는 게 반복됐다(먼 거리에서는
   회전이 균형에 거의 영향 없다는 게 실측 전제였는데, **여백이 0인 극단적으로 가까운
   거리에서는 이 전제가 깨진다**). 두 가지로 대응:
   - `FLUSH_GAP_PX=6` 이하로 붙으면 강제로 살짝 후진(안전망).
   - **진짜 원인**: 전진 스텝(`_go(forward=True, ...)`)이 **고정 크기(0.35초)**라
     여백이 이미 허용범위(20~35px) 안이어도 매번 0까지 밀어붙였다. → 여백이 60px
     미만이면 훨씬 짧은 고정 펄스(`MIN_PULSE_SEC` 크기)로 살살 가도록 수정.
   - **균형 쪽도 거리기반 강제감속 추가**: `very_close = left_gap<=5 and right_gap<=5`
     이면 오차 크기와 무관하게 속도 0.15배로 감속(`vy_scale`).
7. **학습된 균형속도가 튄 값(140~354%p/초)을 그대로 믿어서 폭주**: 검출이 한 프레임
   흔들려서 나온 명백히 비정상적인 값을 그대로 다음 계산에 써서 -57%↔+31%↔-85%로
   폭주했다. → `BALANCE_RATE_SANITY_MAX=1.0`(100%p/초) 넘으면 그 측정을 버림.
8. **마커가 화면 가장자리에 겨우 걸친 채 "찾았다"고 넘어가는 버그**: `raise_arm_and_
   find_marker`가 `marker_pos() is not None`인 순간 바로 만족했는데, 그게 보통 화면
   맨 위(y~14~32)에 겨우 걸친 순간이다. 다음 단계(`align_and_grasp`의 방향보정
   테스트, `calibrate_direction_matrix`)가 작게 움직여보는 것만으로도 마커가 화면
   밖으로 나가서 `RuntimeError: 방향보정 테스트 중 마커를 놓침`으로 죽었다(**여러 번
   재현됨**, y=70에서도 크래시, y=107에서도 크래시). → `MARKER_SAFE_Y=180`으로 크게
   올림(방향보정 펄스의 화면변환계수가 실측상 1m/s당 최대 5000px대까지 나온 적이
   있어서, 작은 테스트 펄스도 100px 넘게 밀 수 있다). `marker_tries`도 5→10→14로
   늘려서 그만큼 더 전진할 예산 확보.
9. **가운데(초록) 정렬을 시작하기도 전에 팔이 이미 가리는 문제**: 8번 수정으로
   마커를 더 깊이(y≥180) 확보하려니, 그만큼 더 전진해서 이번엔 초록이 아예 안
   보이는 상태로 시작하는 경우가 생겼다. `align_and_grasp`이 첫 프레임에서 목표를
   못 찾아 죽는데, 그걸 "정렬 다 된 뒤 가려진 것"으로 오판(원래 그 예외처리는 다른
   상황을 위한 것이었음)해서 정렬을 통째로 건너뛰었다. → `one_cycle`에서 가운데 병
   정렬을 시작하기 전에 실제로 보이는지 먼저 확인하고, 안 보이면 살짝 물러나는
   사전체크 추가(`pick_cycle.py`). **이 물러나는 동작이 마커 y를 다시 180 밑으로
   떨어뜨릴 위험이 있어서 완벽한 해결은 아님 — 미해결로 남음(8번 항목 참고)**.
10. **`run_alignment` 실패 시 대체판정이 엉뚱한 병을 보던 버그**: `run_alignment(mid,
    ...)`(가운데=초록) 정렬이 실패하면 "집게에 가려 안 보이는지"를 확인해서 그러면
    성공으로 간주하는데, 실제로는 최종 목표색(`color`, 예: 빨강)이 보이는지를 검사
    하고 있었다. 서로 무관한 병을 섞어 본 것이라 이 판정이 의미가 없었다. →
    `target_visible(mid)`로 수정.
11. **PIXEL_TOLERANCE를 25→12로 좁힌 게 잘못된 진단이었음**: "성공 오프셋(+3,-19,
    거리19.2px) vs 실패 오프셋(+10,0,거리10px)"을 비교해서 허용오차를 좁히면
    구분될 거라 생각했는데, **실패 쪽이 오히려 거리가 더 짧았다** — 애초에 스칼라
    거리로는 성공/실패가 구분이 안 되는 문제였다. 좁히니 green 정렬 자체가 40스텝
    안에 못 끝나는 새 문제만 생겼다. → **25로 원복**.
12. **`align_and_grasp.py`의 `--max-steps` 기본값 25→40**: 이런저런 수정들 때문에
    수렴에 스텝이 더 필요해져서 늘림(정밀도는 그대로 유지, 스텝만 여유있게).
13. **죽은 코드 발견 및 제거**: `pick_cycle.py`의 `return grasped and gripper_says_
    grasped` **뒤에 절대 실행 안 되는 "병 내려놓기" 블록**이 그대로 남아있었다
    (주석엔 "제거했다"고 돼 있었는데 실제 코드는 안 지워짐). `center_on_target`/
    `target_bottle_x`/`TARGET_BOTTLE_X` 함수군도 예전 방식(베이스를 목표병 앞으로
    직접 옮기는 방식, 지금의 "가운데→옆걸음" 방식으로 대체됨)의 잔재라 삭제.
    안 쓰는 import 3개(`cv2`/`pick_cycle.py`, `numpy`/`approach_board.py`,
    `find_color_blobs`/`align_and_grasp.py`)도 정리.
14. **존재하지 않는 명령어를 안내하던 버그**: `--stop-after-align`이 "`./scripts/
    lekiwi.sh grasp red`로 이어서 하세요"라고 찍는데 `grasp` 서브커맨드 자체가
    없었다. → `--grasp-only` 플래그 + `lekiwi.sh grasp` 서브커맨드 추가(정렬 없이
    지금 자세에서 바로 하강만).

### 4-2. 사용자 요청으로 완화한 것 (2026-08-27, "너무 완벽하게 맞추려 하지 말자")

## 5. 색 검출 (`color_detect.py`) — 오늘 완전히 갈아엎음

### 5-1. 발견한 문제들

- **"빨간" 병은 실제로는 살구색**: 조명에 따라 채도가 44~93까지 떨어져서, 기존
  색범위(S≥65~80)로는 **한 번도 검출이 안 되는 경우가 실제로 있었다.**
- **검은 판(고정캠 배경)이 파란/빨간 병으로 오탐**: `approach_state()`가
  `max_area`를 200000으로 덮어써서 판 전체(면적 138594)가 병으로 잡힌 적도 있었음.
- **나무 바닥이 빨간 병으로 오탐**: 채도 하한을 낮추자 고정캠에서 판 바깥 나무
  바닥이 빨강으로 잡혔고, **가장 큰 빨강 덩어리가 나무(면적 10708)라 진짜 병
  (3551)보다 커서 실제로 집기 목표가 바닥을 겨냥하는 심각한 버그**였다.
- **카메라별 조명이 완전히 다름**: 같은 병인데 고정캠(밝음)과 베이스캠(어두움)의
  채도값이 거의 2배씩 차이 나서, 하나의 색범위로는 한쪽을 조이면 한쪽이 깨졌다.

### 5-2. 최종 해결 구조

1. **`find_board_bbox()`**: 어둡고 채도 낮은 가장 큰 영역 = 판. 이걸로 판 안/밖을 구분.
2. **`find_bottles_on_board()`**: 판 안 + 화면 가장자리에 안 닿은 것만 병으로 인정
   (나무바닥/판반사 오탐을 위치로 걸러냄).
3. **`find_bottles_bright()`(고정캠 전용, 핵심 해결책)**: 색을 먼저 정하지 않고,
   **판 위에서 밝은 덩어리를 먼저 찾은 뒤 그 색조(H)로 이름을 붙인다.** 조명에
   날아간 병도 색조는 남아있어서 이 순서면 잡힌다. `find_color_blobs`가 내부적으로
   이 함수를 1순위로 쓰고, 못 찾으면 기존 색 임계값 방식으로 폴백.
4. **카메라별 프로파일 분리**: `COLOR_RANGES`(고정캠용, `profile='fixed'`)와
   `BASE_COLOR_RANGES`(베이스캠용, `profile='base'`, 채도 하한을 훨씬 높게 잡음).
5. **베이스캠의 배경 오탐 제거**(`approach_board.approach_state`): 병 3개는 크기와
   세로위치가 비슷하다는 전제로, 다른 색들의 폭/세로위치 중앙값에서 크게 벗어나는
   후보는 버림(`BOX_OUTLIER_RATIO=2.5`, `BOX_Y_TOL_RATIO=0.18`).
6. **노랑 색은 완전히 제거**(사용자 확정, 빨강/초록/파랑 3개만 씀) — `DRAW`, 선택지,
   `find_color_blobs` 호출부 전부에서 제거.
7. **가운데 병 색을 위치가 아니라 색으로 자동 학습**(`_latch_middle_color`): 3개가
   깨끗하게(안 겹치고) 보이는 프레임이 `MID_LATCH_FRAMES=2`번 연속 나오면 그때
   화면 가운데 있던 색을 "가운데 색"으로 고정. 병 배치를 바꾸면 재실행 시 새로 학습.

### 5-3. 고정캠 노출 잠김 버그

`fixed_cam_server.py`가 물려있는 카메라(`/dev/video1`)가 **수동노출(auto_exposure=1,
Manual)+brightness=-25로 잠긴 채** 남아있어서 화면 평균밝기가 3.7(사실상 깜깜)이었던
적이 있음. 프로세스를 재시작해도 카메라 자체 설정은 안 풀림. → `_restore_auto_exposure()`
를 서버 기동 시 항상 호출(`v4l2-ctl --set-ctrl=auto_exposure=3 --set-ctrl=brightness=0`).
**재발 시 확인 순서**: 화면이 이상하게 어둡거나 밝으면 `v4l2-ctl -d /dev/video1
--get-ctrl=auto_exposure,brightness`부터 볼 것.

## 6. 시차보정(parallax) — 지금 상태와 미해결 문제

### 6-1. 두 가지 전략이 공존/경쟁했다 (헷갈리지 말 것)

**전략 A (현재 코드가 실제로 쓰는 것): "가운데 병 먼저 정렬 → 옆걸음"**
(`pick_cycle.one_cycle`이 실제로 하는 것)
1. 마커를 **가운데(초록) 병**에 정밀 정렬(`align_and_grasp.py`, `--no-parallax`로
   시차보정 안 씀 — 기준점 자체엔 보정이 필요없고, 오히려 자연스러운 검출 흔들림을
   증폭시켜 해를 끼침).
2. 그 자세 그대로 **옆으로만** 이동해서 마커를 목표 병(빨강/파랑) 위로 가져감
   (`move_marker_to_bottle`). 옆으로만 움직이면 깊이 관계가 거의 유지된다는 게
   전제(아래 6-3 참고 — **이 전제가 항상 성립하진 않았다**).
3. 옆걸음 목표 x좌표는 `parallax.correct(냉동된_병_좌표, parallax.load())`로 계산.

**전략 B (제안/실험만 하고 실제 코드에 안 들어간 것): "cm 실측 기반 계수"**
`calibrate_parallax.py from-distance --camera-to-board D --gripper-offset d`
→ `k = D/(D-d)`. 오늘 `D=47cm`(사용자 어림값), `d=18→20cm`(사용자 어림값, 관찰
피드백으로 상향 조정)로 두 번 계산해서 `config/parallax.json`에 저장함
(현재 `ax=ay=1.7407, bx=by`는 위 계산값). **이 계수는 전략 A의 2단계(옆걸음 목표
계산)에 실제로 쓰이고 있다.**

### 6-2. 오늘 발견한 심각한 한계

- **계산된 목표가 화면 밖(음수)이었다**: `parallax.correct((130,253), 현재계수)`
  = **x=-6.3** — 고정캠 화면(0~640) 밖이다. 즉 시각적으로 마커가 그 지점에
  도달하는 걸 카메라로 확인할 방법이 원리적으로 없다. `move_marker_to_bottle`은
  이 경우 마커가 화면 가장자리 어딘가(x=30~70대)에서 허용오차 안에 들어와
  "도달"로 판정해버리는데, **실제로는 목표보다 한참 못 미친 지점**일 수 있다.
- **사용자가 여러 차례 라이브로 관찰한 것**: "베이스캠을 보면 항상 초록과 빨강
  사이에서 멈춘다, 실제로는 더 오른쪽(화면 x는 더 작은 쪽)으로 가야 한다."
  이건 계산된 목표 자체가 여전히 부족하다는 뜻 — d를 20cm로 올려도(k=1.741) 부족
  하다는 사용자 관찰이 마지막까지 있었다. **d를 더 올리거나(예: 22~25cm), 아예
  cm 기반 모델을 버리고 실제 성공 좌표 2점으로 회귀(`calibrate_parallax.py fit`)
  하는 쪽이 나을 수 있다 — 단, 빨강 성공 좌표가 하나도 없어서(전무) 아직 이 방법을
  못 씀(닭과 달걀 문제).**
- **세로차(marker_y - target_y)가 시도마다 널뛴다**: -90, +60, -67, +27, -8, +10,
  +196, -23 등. 이건 실제로는 "세로"가 아니라 **전후(카메라~로봇) 거리 오차**다
  (고정캠이 위에서 내려다보므로 화면 y가 깊이를 나타냄). 옆걸음만으로는 이 전후
  오차가 항상 작게 유지된다는 전제가 **가끔 크게 깨진다**(원인 불명 — 정렬 시작
  전 베이스 위치의 미세한 차이가 누적되는 것으로 추정, 확실하지 않음).
- **세로차가 아주 작을 때조차(-8, -23, +10 — 초록 성공 사례와 동급) 빨강 하강은
  항상 shoulder_lift 65.5~67.6 사이에서 멈췄다** (`--grasp-lift`를 65/68/70/72로
  다르게 줘도 실제 도달값이 거의 안 바뀜). **이건 이제 정렬 문제가 아니라 그 팔
  자세(빨강 쪽으로 뻗은 자세, shoulder_pan≈-1.7~-1.9)에서의 물리적/토크 한계로
  보인다.** 소프트웨어로 더 건드려서 될 문제가 아닐 가능성이 높음 —
  **로봇 팔을 직접 보고 그 자세에서 뭐에 걸리는지 확인 필요** (사용자에게 요청했으나
  세션 종료 시점까지 답 없음).

### 6-3. `move_marker_to_bottle` 검증했던 것 (실측)

가운데(초록) 정렬 직후 마커-병 세로차 -8px, 옆걸음 후(빨강) 세로차 -8px→변화
없음(실측 1회, 좋은 사례). 하지만 다른 시도에선 옆걸음 후 세로차가 196px까지
벌어진 적도 있음(가운데 정렬을 제대로 안 거치고 대충 시작했을 때). **결론: "옆으로만
움직이면 깊이가 유지된다"는 가정은 가운데 정렬이 정확할 때만 잘 맞고, 가운데 정렬이
부정확한 상태에서 시작하면 크게 깨진다.**

## 7. `align_and_grasp.py`의 마커 튐 감지 (사용자가 "코드에 오류 있는 거 아니냐"고
의심해서 점검한 부분)

`MAX_MARKER_JUMP_PX=130`, `MARKER_SETTLED_PX=40`: 한 프레임 사이 마커가 130px
넘게 움직이면 일단 오탐으로 의심하고 버리되, 같은 위치가 2번 연속 나오면 실제
이동으로 인정한다(원래 2026-08-26에 "이걸 계속 거부하면 정렬이 통째로 실패한다"는
문제 때문에 생긴 방어로직).

**점검 결과**: 이게 실제로 잘못된 판정을 내린 증거는 못 찾음(튐을 인정한 뒤에도
계속 정상적으로 수렴함). 다만 **이론적 약점 하나 발견**: "2번 연속 같은 자리"라는
기준은 노이즈(무작위 오탐)와는 잘 구분되지만, **정적인(항상 같은 자리에 있는)
밝은 반사광이나 케이블 등을 지속적으로 오탐하는 경우엔 구분을 못 한다** — 그런
persistent 오탐은 "2번 연속 같은 자리"를 항상 통과해버리기 때문. **실제로 이게
문제를 일으켰다는 증거는 없지만, 이론적으로는 남아있는 약점이니 참고.**
화면변환계수(카메라→모터 명령 환산)가 실측상 170~5271 px/(m/s)까지 20배 넘게
차이나는 걸 확인함(거리/각도에 따라 요동) — 정상적인 큰 펄스 하나만으로도 130px
기준을 우연히 넘을 수 있다는 것도 확인, 그 자체가 버그는 아님.

## 8. 오늘 시도했다가 버린 것들 (다시 시도하지 말 것 — 이미 안 되는 거 확인함)

- **베이스를 목표 병(빨강/파랑) 앞으로 직접 옮기는 방식**(`center_on_target`,
  `target_bottle_x`) — 판 전체 정렬을 무너뜨리고 마커도 안 보이게 만들어서 폐기.
  코드도 삭제함. **사용자가 명시적으로 "가운데 먼저 → 그 다음 옆으로"를 요청**해서
  전략 A로 완전히 대체됨.
- **PIXEL_TOLERANCE를 좁혀서 성공/실패를 구분하려는 시도** — 스칼라 거리로는
  애초에 구분 안 되는 문제였음(7-2 참고). 25로 원복.
- **수동으로 조금씩 오른쪽으로 밀어보며 눈대중으로 맞추는 방식** — 판 밖으로
  두 번이나 오버슈트했고, `interpolate()`에 없는 키워드 인자(`keep_gripper`)를
  넘겨서 팔이 하강 자세에서 멈춘 채 스크립트가 죽는 사고도 냈다(다행히 안전하게
  복구함, 병도 안 넘어짐). **사용자가 이 방식 대신 정식 절차(베이스정렬→가운데정렬
  →보정된 만큼 옆걸음)를 쓰라고 명시적으로 지적함 — 앞으로도 이 정식 절차만 쓸 것.**

## 9. 오늘 세션에서 겪은 운영상 사고들 (재발 방지용 기록)

- **`pkill -f "패턴"`을 SSH 원격 명령으로 보내면, 그 명령 문자열 자체가 패턴에
  걸려 원격 쉘 자신을 죽이는 사고가 날 수 있다**(이전 세션에서 실제로 겪음).
  PID 기반 kill을 쓸 것.
- 로봇이 뭔가 이상해지면(예: 베이스가 계속 회전하며 병이 3개↔2개로 반복 전환되며
  발산) **소프트웨어로 계속 되돌리려 하지 말고 사람이 직접 보고 손으로 리셋하는
  게 빠르다.** 오늘 실제로 이런 발산이 한 번 있었고, 사용자가 직접 확인 후 리셋함.
- `arm_shoulder_lift.pos`가 명령과 전혀 다른 값(예: 9.9, 목표 68)으로 튀는 걸
  한 번 봤는데, 재확인해보니 일시적 현상이었고 실제로는 정상 범위(-5.8 등, 안전한
  값)로 돌아와 있었다. **비정상 관절값을 보면 일단 멈추고 재확인할 것, 하지만
  한 번의 이상값만으로 "고장"이라 단정하지 말고 다시 읽어볼 것.**
- **매 사이클 시작 전 반드시 `home` → 병 3개 위치 확인.** 실패한 사이클 후 병이
  살짝 밀리거나(수십 px) 판 밖으로 완전히 떨어진 적(초록 1회)도 있었음.

## 10. 성공/실패 통계 (2026-08-27 세션, 이전 세션 포함)

- **초록(green)**: 이전 세션 4회 성공 + 오늘 세션 최소 3회 이상 성공(정확한 횟수는
  세션 로그 참고). **신뢰도 높음.**
- **빨강(red)**: 오늘만 20회 넘게 시도, **0회 성공.** 정렬(마커 위치)은 후반부로
  갈수록 계속 개선되어 마지막 몇 번은 초록 수준(오차 한 자릿수 px, 세로차 10~23px)
  까지 좋아졌는데도 하강이 매번 65.5~67.6 사이에서 막혔다.
- **파랑(blue)**: **오늘 단 한 번도 시도 안 함.** 다음 세션에서 시도해볼 가치 있음
  (빨강과 대칭 위치라 비슷한 문제가 있을 수도, 없을 수도 있음 — 실측 전엔 모름).

## 11. 다음 세션이 우선적으로 시도해볼 것 (제안, 확정 아님)

1. **빨강 하강 물리적 한계 규명**: 사용자와 함께 직접 로봇 팔을 보면서, 그 자세
   (shoulder_pan≈-1.8)에서 하강할 때 정확히 어디가 걸리는지 육안 확인. 서보 토크
   부족이면 다른 접근각(wrist_flex/elbow_flex 조합을 바꿔서 같은 위치를 다른
   자세로 접근)을 시도해볼 것.
2. **파랑(blue) 테스트**: 빨강과 대칭이니 같은 파이프라인으로 시도해보고, 같은
   문제(하강 막힘)가 있는지 없는지부터 확인. 없다면 "빨강만의 특수한 문제"라는
   뜻이고, 있다면 "가운데에서 먼 병 전체의 문제"라는 뜻이라 원인 규명 방향이
   달라짐.
3. **시차보정 2점 회귀**: 빨강이 한 번이라도 성공하면 그 순간의 (마커,병) 좌표를
   `calibrate_parallax.py record --color red`로 즉시 기록하고, 초록 샘플과 함께
   `fit`으로 실제 기울기(k)를 계산 — cm 어림값보다 훨씬 정확할 것.
4. **판 평행도 확인 기능**(사용자 아이디어, 미구현): 베이스캠에서 판의 좌우 모서리가
   화면 대칭으로 보이는지 확인해서 로봇이 판과 정확히 평행한지 판정하는 기능.
   시간 부족으로 미구현 — 사용자가 "하고 싶다"고 명시적으로 관심 표현함.
5. **`config/parallax.json`의 `d`(gripper-offset)를 더 올려서 재시도**: 마지막
   피드백이 "20cm로도 부족하다"였으므로, 22~25cm 범위로 다시 계산해서 시도해볼
   가치 있음. 계산 명령:
   ```bash
   ./venv/bin/python scripts/calibrate_parallax.py from-distance \
     --camera-to-board 47 --gripper-offset <새값> --anchor-x 314 --anchor-y 328
   ```
