## 1. 개요

본 문서는 시스템 구축 과정에서 발생한 결함과 그 해결 방법을 기록한다.
분류 기준은 결함이 나타난 부품이 아니라 **근본 원인**이다. 부품별 분류는
원인을 이미 아는 경우에만 유효하나, 원인별 분류는 새로운 결함을 만났을 때
해당 유형을 먼저 특정할 수 있다.

각 절 서두의 **원리**는 본 프로젝트를 벗어나 다른 로봇·다른 시스템에도
적용 가능한 부분이다.

### 1.1 결함 분포

| 분류 | 건수 | 대표 결함 |
|---|---|---|
| 3.1 기준 좌표계 오류 | 5 | 라이다 장착각 30° 오차로 지도 전량 폐기 |
| 3.2 센서 전처리 부재 | 5 | 노이즈 반환이 가상 벽으로 기록 |

## 2. 공통 관찰: 실패의 가시성

원인 분류와 별개로, 해결에 소요된 시간을 결정한 요인은 **실패가 관측
가능했는지 여부**였다.

| 결함 | 관측된 현상 | 실제 상태 | 소요 |
|---|---|---|---|
| 라이다 장착각 30° 오차 | 오류 메시지 없음. 지도 품질만 저하 | 지도 전량 폐기 | 수일 |
| IMU 통신 두절 | 오류 메시지 없음. 지도가 확장되지 않음 | Cartographer 무한 대기 | 수시간 |
| 정합 지표 편향 | 오류 메시지 없음. 93% 신뢰도로 보고 | 위치 오판정 | 수시간 |
| 배포 시 교정값 소실 | 오류 메시지 없음 | 다음 SLAM 수행 전까지 미인지 | — |
| `--tf` 인자 누락 | `/odom` 은 정상 발행 | 상위 계층 전면 실패 | 수시간 |
| 경로 추종 중단 | `Goal failed` + `Control loop missed` **로그 출력** | CPU 포화 | **1시간** |

**결론**: 오류 메시지를 출력한 결함은 1시간 내에 해결되었으나, 값이 계속
출력되면서 내용만 틀린 결함은 수일이 소요되었다. 이에 따라 계층별 자동 점검
도구(`lekiwi_setup.launch.py`, `check_config.py`)를 도입하여 무증상 결함을
가시화하였다.

## 3. 원인별 분석

### 3.1 기준 좌표계 오류 — 캘리브레이션

**원리** 개별 측정값이 모두 정확하더라도 기준 좌표계가 잘못되면 전체 결과가
왜곡된다. 이 오류는 수집된 데이터만으로는 검증되지 않으며, 물리적 시험이
필요하다.

| # | 문제 상황 | 원인 | 해결 방법 |
|---|---|---|---|
| 1 | 주행 방향과 화면상 로봇 방향이 불일치. AMCL 위치추정이 지속적으로 이탈 | URDF 의 `base_link → lidar_link` yaw 가 −30° 로 설정됨 | yaw 를 0° 로 수정. 해당 설정으로 작성된 지도는 전량 폐기 후 재작성 |
| 2 | 1차 수정 후에도 방향 불일치 | 옴니휠 `ANGLES` 를 바퀴 **장착 방위**로 해석. 실제로는 **구름 방향**이며 90° 차이 | `ANGLES` 원복, URDF 만 수정 |
| 3 | 회전 오도메트리가 실제 회전량과 불일치 | lerobot 기본값 `base_radius = 0.125` 가 실측 대비 9% 오차 | 3회전 시험으로 실측 → `0.13647` |
| 4 | 옴니 로봇이 횡방향으로 이동하지 않음 | Nav2 `motion_model` 기본값 `DiffDrive` 가 `vy` 성분을 무시 | `"Omni"` 로 변경. AMCL 도 `OmniMotionModel` 적용 |
| 5 | 특정 구역 진입 불가 | `robot_radius 0.18` 이 실측 최외곽 0.158 m 대비 과다 | 0.16 으로 조정 필요 (**미적용**) |

**원리적 제약**  라이다 장착각은 자기반사 데이터만으로 결정되지 않는다.
옴니휠 3개가 120° 간격으로 배치되어 `-30 / +90 / -150` 세 후보가 데이터와
동일하게 부합한다. 각도 자체는 1° 이내로 산출되나 대응 바퀴는 특정되지 않는다.

**병진 운동이 필요한 이유**  라이다가 회전 중심(`base_link` 원점) 상부에
위치하므로, 제자리 회전 시에는 장착각과 무관하게 스캔이 동일하게 정합된다.
장착각은 병진 운동에서만 관측 가능하다.

**적용 결과**  `lekiwi_lidar_test.launch.py` 가 출발·도착 스캔을 오도메트리
이동량만큼 정합하여 잔차 최소 각도를 산출한다. 합성 데이터 검증에서
−30 / +90 / −150 / +17.5° 를 모두 0.2° 이내로 복원하였다.

> **일반화**  데이터가 복수의 해에 동일하게 부합하는 경우, 동종 데이터를
> 추가 수집해도 해결되지 않는다. 다른 종류의 관측을 도입해야 한다.

### 3.2 센서 데이터 전처리 부재

**원리** 라이다 출력은 전부 거리값 형식이나, 그중 일부는 물리적 측정에
해당하지 않는다.

| # | 문제 상황 | 원인 | 해결 방법 |
|---|---|---|---|
| 1 | 장애물이 없는 실내 중앙에 가상 벽 생성. 접근하면 소멸하고 다른 위치에 재발생 | 약한 반사(노이즈)를 유효 반환으로 처리 | `--min-intensity 25` 적용. 실측 결과 본 현상의 주원인 |
| 2 | 원거리에 가상 벽 형성 | `max_range 9.0`. Cartographer 는 범위 **내** 반환을 전부 점유로 처리하며, 자유공간은 범위를 **초과한** 반환으로만 갱신됨 | `max_range 4.5` 로 하향 |
| 3 | 자기 바퀴가 벽으로 기록됨 | 옴니휠 3개가 시야의 30.4% 차폐. 해당 방향의 미탐지는 자유공간이 아님 | `--mask-wheels` 적용. 사각지대는 `deadbeam.py` 로 실측 |
| 4 | 회전 중 스캔 왜곡. 0.60 rad/s 에서 연속 스캔의 21% 불일치 | 1회전 소요 164 ms. 스캔 중 로봇이 이동 | 회전당 오도메트리 yaw 변화량 기반 디스큐 적용 |
| 5 | 경로 계획이 개시되지 않음 (`Failed to create plan with tolerance`) | 고립 점유 셀이 팽창하여 로봇 현재 위치를 점유로 처리 | `despeckle_map.py` 로 고립 셀 제거 (실측 12개 제거로 해소) |

**주의: `max_range` 의 동작**  값이 클수록 유리하지 않다. 범위를 초과해야
자유공간으로 갱신되므로, 과대 설정 시 원거리 노이즈가 전부 벽으로 기록된다.

**주의: 후처리 과다**  `despeckle_map.py --min-neighbors 3` 을 벽이 얇게
작성된 지도에 적용한 결과 379개 중 69개(18%)가 제거되었으며, 그중 일부는
실제 외벽이었다. 외벽 결손 시 Nav2 가 해당 구간으로 경로를 생성할 수 있다.
얇은 지도에는 `2` 를 적용하고 결과를 육안 대조해야 한다.

**디스큐 구현 시 유의사항**  `wz × T` 방식은 `poll()` 이 `read(4096)` 에서
블록되어 `T` 가 실제 0.156 s 대신 0.30 s 로 측정되므로 사용할 수 없다.

### 3.3 평가 지표 편향

**원리** 알고리즘이 아니라 최적화 목표 함수가 잘못된 사례다. 최적화는 지정된
기준을 정확히 충족하였으며, 기준 자체가 부적절하였다.

| # | 문제 상황 | 원인 | 해결 방법 |
|---|---|---|---|
| 1 | 자동 위치추정이 실제와 다른 구역 선택 (오답 93%, 정답 67%) | 지표가 "스캔 끝점의 점유 셀 적중률". 점유 셀이 많은 구역을 구조적으로 선호 | 거리 변환 기반 지표(끝점–최근접 벽 거리, ICP 잔차와 동일)로 교체 |
| 2 | 지도 범위 외부 자세가 83%로 평가됨 | 범위를 벗어난 끝점을 계산에서 **제외**. 불일치 빔을 선택적으로 배제 가능 | 제외 대신 최대 벌점 부여. 동일 자세 재평가 시 34%, 30 cm 초과 빔 48.6% |
| 3 | 미탐색 영역이 최적해로 선택됨 (93.2%) | 미지 영역 빔에 벌점 없음 | 로봇 위치 반경 3셀 내 자유 셀 부재 시 후보에서 제외 |
| 4 | 재정합 후 69 cm 오위치 발생 | 좁은 탐색창이 국소 최적에 수렴. 로봇이 실제로 목표점에 도달하지 못한 경우 | 보정 결과가 기존 AMCL 대비 열등하면 발행하지 않는 가드 추가 |
| 5 | 루프 클로저 약 15% 허위 검출 | `min_score 0.65` | `min_score 0.78`, `linear_search_window 2.0` 로 재매핑 필요 (**미적용**) |

**판별 근거는 평균이 아닌 분포의 꼬리**

| 가설 | 적중률 | 끝점의 20 cm 초과 비율 |
|---|---|---|
| 정답 | 67% | **0.0%** |
| 오답 | 93% | **5.9%** |

스캔 끝점이 개방 공간에 위치하는 자세는 물리적으로 성립하지 않는다. 평균
지표가 낮더라도 이상치가 없는 해가 정답이다. 이상치 상한(0.30 m)을 적용하여
소수 빔이 평균을 지배하지 않도록 하였다.

**설계 지침 1**  목표 함수에 데이터를 배제할 수 있는 경로가 존재하면 최적화가
이를 이용한다. 배제 대신 벌점을 부여해야 한다.

**설계 지침 2**  운용자가 확인한 물리적 사실이 지표에 우선한다. 로봇이 시작
지점에 있음에도 전역 탐색은 목표지점을 93.6%로 선택하였다. 시작 지점은 지도
경계에 인접하여 불리하고, 목표지점 주변은 매핑 밀도가 높아 유리하기 때문이다.
위치가 알려진 경우 `set_pose.py` 로 직접 지정하고, `refine_pose` 는 ±0.25 m /
±20° 범위의 미세 조정에만 사용한다.

**신뢰 불가 도구**  `find_pose.py --global` 은 편향된 적중률 지표를 사용하므로
다중 구역 지도에서 사용하지 않는다.

### 3.4 실행 환경의 한계

**원리** 알고리즘이 정확해도 연산·통신·전원 자원이 부족하면 실패한다. 이때
장애는 원인과 무관한 지점에서 표면화된다.

| # | 문제 상황 | 원인 | 해결 방법 |
|---|---|---|---|
| 1 | `Goal failed` 발생. 주행 자체는 목표점 5.8 cm 이내 도달 | 제어 주기 10 Hz 설정 대비 실측 7.7 Hz. Behavior Tree 의 `compute_path_to_pose` 응답 대기 타임아웃 | `controller_frequency 5.0` 으로 하향. 이후 `Control loop missed` 경고 0건 |
| 2 | 유휴 상태 CPU 사용률 244% (4코어 400% 기준) | abo 브리지의 TF 리스너가 `/tf` 56 Hz 를 Python 에서 파싱하며 46% 점유 | `/amcl_pose` 구독으로 전환 → 2.1%. `/odom` 50→25 Hz 조정 → 36%→23%. **총 58% 확보** |
| 3 | `SerialException: multiple access on port?` 로 베이스 노드 종료 | 서보 9개가 단일 반이중 버스 사용. Linux 는 시리얼 포트 배타 개방을 강제하지 않아 동시 개방 후 충돌 (실측 60회 중 4회 실패) | `/lekiwi_base/set_bus` 서비스로 버스 소유권 명시적 이양 |
| 4 | 지도가 확장되지 않으며 오류 메시지 없음 | IMU I2C `Errno 5` 로 노드 종료 → Cartographer 가 `Queue waiting for data: (0, imu)` 상태로 대기 | 3회 재시도 및 샘플 스킵 적용. 런치에 `respawn=True` 설정. 버스 완전 정지 시 전원 재인가 필요 |
| 5 | 로봇 전원이 임의로 차단됨 | 배터리 미연결. 충전기 단독 공급 상태에서 서보 토크 인가 시 전류 급증을 완충할 수단이 없음 | **미해결.** 배터리 연결 전까지 구동계 시험 불가 |

**제어 주기 관련**  달성 불가능한 10 Hz 설정보다 안정적으로 유지되는 5 Hz 가
우수하다. 0.10 m/s 주행 시 2 cm 간격 재계획에 해당하며 충분하다.

**CPU 분석 시 유의사항**  MPPI 컨트롤러는 현재도 최대 점유 항목이다(152%).
본 항목의 요지는 MPPI 가 문제가 아니라는 것이 아니라, **개선 가능한 낭비가
다른 지점에 있었으며 초기 대응(MPPI 파라미터 축소)이 대상을 잘못 지정하였다**
는 점이다. 참고로 빈 rclpy 노드의 유휴 비용은 executor 종류와 무관하게 약 6%
(single 6.0 / multi(2) 6.4 / multi(4) 6.8)이며, 이를 초과하는 부분은 응용
코드에 기인한다.

### 3.5 이식 시 고유값 고정

**원리** 검증된 **값**과 값이 **저장되는 위치**를 분리하지 않으면, 복제 시
값이 함께 이동하거나 덮어쓰기된다. 3.1 은 값 자체가 부정확한 경우이고, 본
항목은 값은 정확하나 참조 위치가 부적절한 경우다.

| # | 문제 상황 | 원인 | 해결 방법 |
|---|---|---|---|
| 1 | 다른 기체에서 교정을 수행해도 반영되지 않음. URDF 경로가 원 기체 파일을 참조 | 런치 파일의 `DEFAULTS` 에 기체 고유값이 하드코딩되어 프로파일보다 우선 적용 | 런치가 `lekiwi_profile.sh` 를 **판독**하도록 변경 |
| 2 | 코드 수정 후 재배포 시 실측 교정값이 기본값으로 복귀 | 배포 스크립트가 프로파일을 무조건 재생성 | 기존 프로파일 보존. `--reset-profile` 지정 시에만 덮어쓰기 |
| 3 | 런치가 존재하지 않는 파일 참조 (1일 내 2회 발생) | 파일명에 기체 번호 포함(`lekiwi06.urdf`, `lekiwi06_cartographer.lua`)으로 모든 참조 지점이 파일명을 추정해야 함 | 파일명에서 기체 번호 제거(`lekiwi.urdf`, `lekiwi_cartographer.lua`). SD카드당 기체 1대이므로 번호는 정보를 추가하지 않음 |
| 4 | 다른 기체에서 `scservo_sdk` 미검출 | `lerobot060_venv` 경로 하드코딩. 대상 기체에는 `lerobot_venv` 만 존재 | 경로명이 아닌 `scservo_sdk` 실제 존재 여부로 탐색 |
| 5 | 배포된 구성이 최신 상태와 불일치 | 배포 목록에 런치 8개·시험 노드 3개 누락. 프로파일 템플릿에 구버전 값(`LIDAR_YAW="-30.0"`) 잔존 | 목록 갱신 및 템플릿 현행화 |
| 6 | 문서에 기재된 교정 도구가 존재하지 않음 | `deadbeam.py` 가 문서 5개소에서 참조되나 원 SD카드에만 존재하여 미이관 | 재작성 후 배포 목록에 포함 |

**조치 결과**  기체 고유값의 단일 출처를 `lekiwi_profile.sh` 로 확정하였다.
부수 효과로 `lidar_yaw` 중복 정의가 3개소에서 2개소(프로파일·URDF)로
감소하였고, 런치의 파일명 추정 로직이 제거되었다.

**기체별 차이**

| 항목 | lekiwi01 | lekiwi05 |
|---|---|---|
| IMU | 탑재 (BMI160) | **미탑재** |
| 카메라 | 1대 | 2대 |

IMU 미탑재 기체는 `lekiwi_cartographer.lua` 에서 `tracking_frame = "base_link"`,
`use_imu_data = false` 로 수정해야 한다. 미수정 시 SLAM 이 무증상 정지한다.

동일 SD카드를 다른 몸체에 장착한 사례에서 라이다 미탑재, CH343 2개, 카메라
3대, USB 허브 3단 중첩 구성이 확인되었다. `lekiwi_setup.launch.py` 는 설정
파일과 정적 TF 를 정상 판정하고 장치·토픽만 실패 판정하여 원인을 정확히
분리하였다.

### 3.6 소프트웨어 구조 결함

**원리** 3.4 가 자원 부족에 기인한다면, 본 항목은 자원이 충분한 상태에서
구조적 오류로 발생한 장애다.

셸 파이프라인 관련 결함 2건(#7, #8)은 동일 계열이다. 파이프는 데이터 경로와
제어 흐름을 동시에 바꾸므로, **내용이 대체되거나 종료 상태가 뒤집혀도 오류로
드러나지 않는다.** 검증 로직에 파이프를 쓰지 않는 것이 안전하다.

#### 3.6.1 런타임 구조

| # | 문제 상황 | 원인 | 해결 방법 |
|---|---|---|---|
| 1 | ZMQ 연동 시 ROS 콜백 전체 정지 | `SingleThreadedExecutor` 는 콜백을 순차 처리하므로 블로킹 호출 1건이 전체를 차단 | `MultiThreadedExecutor` + 콜백 그룹 분리 |
| 2 | abo 브리지 전체 종료. 왕복 미션이 복귀 단계 미개시 | 콜백에서 발생한 `TimeoutExpired` 가 외부로 전파 | 콜백 전체를 예외 처리로 포괄. 재정합 실패 시에도 진행 |
| 3 | `/odom` 은 정상 발행되나 TF 부재로 상위 계층 실패 | `run_base.sh` 실행 시 `--tf` 인자를 수동 부착해야 함 | 런치가 항상 부착하도록 변경 |
| 4 | 노드 종료 후에도 CPU 점유 지속 | `stop_nav2.sh` 가 `component_container_isolated` 미포함 | 종료 대상 패턴 보강 |
| 5 | 종료 시마다 오류 2행 출력 및 5초 지연 | `ros2 run` 의 Python 래퍼가 실제 바이너리를 자식 프로세스로 실행하여 SIGINT 미전달 | 바이너리 직접 실행. 종료 시간 29→24초, 프로세스 2→1개 |
| 6 | `robot_state_publisher` 즉시 중단 | URDF 를 `-p robot_description:="$(cat ...)"` 로 전달 시 다행 XML 이 인자 파서 손상 | 파일 경로로 전달 |
| 7 | 생성된 설정 파일에 공백 1자만 기록. 이후 패키지 5종이 `no installation candidate` 로 연쇄 실패 | `SUDO() { echo " " \| sudo -S ...; }` 에 파이프 입력 시 내용이 비밀번호로 대체됨 | 임시 파일 경유 후 `install` 로 이동 |
| 8 | 저장소가 정상인데 검증 단계가 **실패로 판정**하여 설치 중단 | `apt-cache policy X \| grep -q PAT` 에서 `grep -q` 가 첫 매칭 후 즉시 종료 → 앞 명령이 SIGPIPE 로 141 종료 → `set -o pipefail` 이 141 을 파이프라인 상태로 채택 → 조건 반전 | 파이프 제거. 출력을 변수에 담고 `case` 로 판정 |

#### 3.6.2 시험 도구 자체의 결함

| # | 문제 상황 | 원인 | 해결 방법 |
|---|---|---|---|
| 8 | 회전 시험으로 축척 검증 불가 | 왕복 구조에서는 `BASE_R` 오차가 상쇄되어 물리적으로 원위치 복귀 | 편도 방식으로 변경. 왕복은 `--round-trip` 선택 사항 |

### 3.7 진단 과정의 시행착오

**원리** 근거가 뒷받침하는 범위를 초과하여 원인을 단정한 사례다. 시스템
결함과 성격이 다르므로 분리하여 기록한다.

| # | 판단 | 실제 | 근거의 한계 |
|---|---|---|---|
| 1 | 위치추정 상태에서 자율 주행 시험 진행 | **벽면 충돌 발생** | 정합도 미달 상태에서 무인 6사이클 전진 수행. 자체 출력의 "빔 100% 관통" 경고 미반영. `collision_monitor` 우회하여 `/cmd_vel` 직접 발행 |
| 2 | "충전 중이므로 전원 미공급" | SD카드가 다른 몸체에 장착된 상태 | 근거는 "서보 무응답 + 포트 정상 개방"까지만 지지. 운용자의 "모터 LED 점등" 정보로 정정 |
| 3 | "갱신 스크립트가 위치추정을 손상" | 운용자가 로봇을 수동 이동 | 정합도가 오히려 개선된 데이터가 있었음에도 선행 결론 |
| 4 | "바퀴 마스크 위치 부정확" | 실측 결과 1° 이내 일치 | 강도 필터가 해당 빔을 선행 제거하여 마스크 효과가 관측되지 않은 것 |
| 5 | "유효 빔 수 부족" | 환경 차이 | 필터 해제 시 371/720 으로 정상 |
| 6 | "`twist.angular.z` 사용 불가" | 회전 구간만 재측정 시 **100% 정확** | 측정 구간에 정지 시간 포함 |
| 7 | "지도 미탐색 65%" | 실내 기준 7.4% | 벽 외부 영역까지 계수 |
| 8 | "재부팅 후에도 IMU 미검출" | 재부팅 미실시 상태 | 운용자 발언 오독 |

**반복 관찰된 양상**

- 정합 지표의 결함은 운용자가 2회 지적한 후에 검토되었다
- 시작 위치에 관한 정보는 3회 전달된 후에 지표 추종이 중단되었다

운용자는 지표가 접근할 수 없는 로봇의 물리적 상태 정보를 보유한다. 지표와
운용자 정보가 상충하는 경우 운용자 정보를 우선한다.

**이후 적용된 운용 원칙**  정합도 80% 미만 시 전진 금지, 회전만 수행,
단계별 개별 검증, `collision_monitor` 우회 금지.

## 4. 정상 동작이나 오작동으로 오인되는 현상

| 현상 | 정상인 이유 | 대응 |
|---|---|---|
| 정지 중 `/amcl_pose`·`/particle_cloud` 미발행 | `update_min_d 0.10` / `update_min_a 0.15` 초과 이동 시에만 갱신. 정지 중에는 신규 정보가 없으며, 동일 정보로 재추출 반복 시 파티클 고갈로 필터가 손상됨 | 표시 목적에 한해 `ros2 service call /request_nomotion_update std_srvs/srv/Empty` |
| RViz 에 파티클 미표시 | `/particle_cloud` 는 BEST_EFFORT 로 발행 | 디스플레이 Reliability 를 `Best Effort` 로 설정 |
| 방향 표시가 이전 위치에 잔존 | `/odom` 기반 Odometry 디스플레이의 `Keep: 30` 설정. 재정합 후에도 기존 표시는 갱신되지 않음 | 디스플레이 비활성화 후 재활성화 |
| 텔레오퍼레이션 무반응 | `collision_monitor` 가 최종 관문. 라이다 부재 또는 스캔 지연 1초 초과 시 모든 명령을 폐기 | 라이다 상태 및 스캔 지연 확인 |
| Nav2 기동 중단 | `docking_server` 설정 부재 시 `Charging dock plugins not given!` 로 configure 실패, `lifecycle_manager` 가 전체 기동 중단 | 미사용 시에도 최소 설정 유지 |
| AMCL `Waiting for map....` | `map_server` 가 `/map` 을 TRANSIENT_LOCAL 로 1회 발행. 구독 지연 시 수신 실패 (실측 18 ms 차) | `/map_server/load_map` 재호출 |
| 원격 RViz 에 지도 미표시 | TRANSIENT_LOCAL `/map` 이 무선 구간의 지연 구독자에게 미전달 | `map_view_publisher.py` 로 로컬 발행 |
| 지도가 이중으로 작성됨 | Cartographer 가 센서보다 선행 기동 시 빈 데이터로 최초 서브맵 생성 | 런치의 14초 지연 유지 |

**`costmap_2d` 값 인코딩**  253(inscribed) → 99, 254(lethal) → 100,
255(unknown) → −1. 치명 영역을 결정하는 파라미터는 `inflation_radius` 가
아니라 `robot_radius` 이다.

## CRLF 줄바꿈이 섞인 프로파일

| | |
|---|---|
| **문제상황** | `check_config` 가 `[실패] 라이다 /dev/ttyUSB0` 을 내는데, 정작 `/scan` 은 정상(6 Hz)으로 나온다. `ls /dev/ttyUSB0` 도 멀쩡히 있다. |
| **원인** | `lekiwi_profile.sh` 가 CRLF 였다. `source` 하면 값 끝에 `\r` 이 붙어 `LEKIWI_LIDAR_PORT='/dev/ttyUSB0\r'` 가 되고, 이는 존재하지 않는 경로다. 런치는 자체 파서가 `.strip()` 을 해서 멀쩡했고, 셸을 거치는 쪽만 깨져 증상이 모순돼 보였다. |
| **해결방법** | `sed -i 's/\r$//' ~/lekiwi_profile.sh`. 저장소에는 `nav/.gitattributes` 로 `eol=lf` 를 못 박고, `deploy_lekiwi.py` 가 전송 직전에 CRLF 를 LF 로 바꾸며 경고하도록 했다. |
| **확인** | `bash -lc 'source ~/lekiwi_profile.sh && python3 -c "import os;print(repr(os.environ[\'LEKIWI_LIDAR_PORT\']))"'` |

증상과 원인이 다른 층에 있는 전형적인 예다. 값을 눈으로 비교하면 똑같아 보이므로
반드시 `repr()` 로 찍어볼 것.
