# LeKiwi 약통 픽업 데모 설계

날짜: 2026-08-12
목적: 공학경진대회 제출용 데모
관련 저장소: 에이보 본체(`robot_ws`, 별도 저장소)의 `lekiwi_tool.py`/`lekiwi_control.py`/
`lekiwi_command_node.py`와 SSH 인터페이스로 연동. 이 저장소는 그 트리거를 받아 실제
비전+집기를 수행하는 쪽만 담당한다.

## 배경

로봇공학 워크스페이스(`robot_ws`)에서 개발 중인 음성 대화 로봇 "에이보"와, 별도로 보유한
LeKiwi(팔+바퀴, LeRobot 프레임워크 기반) 로봇을 연동해, 2주 뒤 공학경진대회에 제출한다.

**대회 형식**: 1차 영상 제출(약 2주 후 마감) → 2차 라이브 시연(1차 직후, 며칠 안).
**배점**: 문제정의및필요성 15 / 창의성·혁신성 20 / 기술적완성도 25 / 실용성 10 /
성능및결과검증 20 / 발표및시연가능성 10 (총 100)
**심사위원**: 학교 교수님들, 피지컬 AI 비전문가로 예상됨 — 기술적 정교함보다 시연이
직관적으로 인상적인지가 중요할 수 있음. 단, 배점표 자체는 명시적 항목 기준이라 실제
검증된 결과물을 요구한다.

**부가 목적(대회와 무관, 코드/일정에 영향 없음)**: 이 시스템("카메라로 물체 위치를
인식해 로봇팔이 정밀하게 집는다")은 산업 자동화의 "빈 피킹(bin picking)/픽앤플레이스
자동화"와 기술적으로 동일한 형태라, 대회 종료 후 **서사만 바꿔** 포트폴리오용(기업
대상)으로 재활용 가능 — "환자를 위한 돌봄" 대신 "공정 자동화: 비전 기반 부품 피킹"으로
재편집. 코드 변경 없이 내레이션/타이틀만 교체하면 되므로 이번 계획에는 반영하지 않음.
향후 확장 후보(이번 스코프 밖): 불량품/정상품 분류 피킹, 임의 자세 물체 피킹.

**경쟁 환경**: 다른 팀이 바퀴 베이스+양팔+SLAM+라이다 기반의 "재난상황 탐색" 로봇을
이미 높은 완성도로 준비 중인 것으로 파악됨(전언 기준, 미확인). 저희가 가진 자원(2주,
LeKiwi 표준 구성 — SLAM/라이다 없음, 라즈베리파이4+노트북 RTX 3070 8GB 40W캡)으로는
같은 축(탐색 정교함/센서 스펙)에서 정면 승부하기 어렵다고 판단.

## 전략: 비교 축 전환

경쟁팀과 "탐색 정교함"으로 경쟁하는 대신, **"자연어로 소통하며 도와주는 돌봄 로봇
생태계"**로 차별화한다:
- 문제 설정: 누워있는 환자가 스스로 주울 수 없는 약통을 로봇에게 음성으로 부탁
- 두 로봇(에이보=대화형 AI, LeKiwi=이동형 매니퓰레이터)이 하나의 시스템처럼 연동
- 값비싼 라이다 없이 카메라+AI만으로 문제를 푸는 저비용 접근

배점표상 기술적완성도(25)+성능및결과검증(20) = 45점이 "얼마나 화려한가"가 아니라
"실제로 검증된 결과가 있는가"를 요구하므로, **스코프를 작게 잡고 확실히 되는 것**을
우선한다. 창의성(20)+문제정의(15) = 35점은 위 차별화 서사로 겨냥한다.

## 스코프

**포함**:
- 음성 명령("약 좀 찾아서 갖다줘") → 에이보 → SSH → 노트북에서 실행되는 비전+집기
  스크립트 → LeKiwi가 책상 위 눈앞의(고정된 크기/자세) 약통을 YOLO로 찾아 정밀하게 집음
- 그 앞 단계로, 이미 검증된 음성→LeKiwi 이동 트리거(`move_skill.py`)를 오프닝 시연으로
  같이 사용(별도 개발 불필요)
- 반복 시행 기반 성공률/소요시간 기록(성능 검증 자료 겸 영상 소재)
- 실패 시 다운그레이드 가능한 폴백 플랜(아래 참고)

**명시적으로 제외**:
- SLAM/자율주행/장애물회피 — 대상 경쟁력 축이 아니라고 판단해 배제
- 바닥 전체 탐색(open-floor search) — 책상 위 좁은 범위로 한정
- 임의의 자세/방향으로 놓인 물체 처리 — 약통의 종류/크기/놓는 자세를 고정해 문제를
  단순화
- 아이작심(Isaac Sim) 실시간 연동 — 별도 엔지니어링 부담이 크고 핵심 리스크(라이브
  환경 불확실성)를 해결해주지 않음. 여유가 생기면 1차 영상용 비실시간 클립(사전 검증
  장면)으로만 검토, 이번 스코프의 필수 요소 아님
- 그리퍼 재시도 로직(실패 시 재시도) — 시간 부족으로 이번 스코프 밖, 실패 시 안내만
- 영상 조작(좌표 하드코딩 등으로 실제로 안 되는 걸 되는 것처럼 편집) — 실제 반복
  시행 중 잘 된 테이크를 편집하는 것은 허용, 가짜 결과 제시는 배점표 취지(성능 및
  결과 검증)에 위배되므로 하지 않는다

## 데모 시나리오

1. **오프닝**: "에이보야, 르키위 오른쪽으로 돌려줘" 등 → 이미 실물 검증된 이동 트리거
   → 음성으로 로봇을 통제한다는 것을 관객에게 먼저 각인
2. **하이라이트**: "에이보야, 저 약 좀 찾아서 갖다줘" → 신규 개발할 비전+집기 파이프라인
   실행 → 성공 시 에이보가 "가져왔어요!" 음성 안내

심사위원이 피지컬 AI 비전문가로 예상되므로, 시연/영상 내레이션으로 "지금 로봇이 카메라로
위치를 계산해 팔을 뻗고 있다"는 식의 설명을 곁들여 인상을 명확히 전달한다.

## 환경 통제 (제약을 걸어 신뢰성 확보)

- **장소**: 책상(고정 높이, 좁은 범위)으로 예상 — **미확정, 확인 필요**(아래 열린 질문)
- **대상 물체**: 실제 빈 약통 사용. 다만 **종류/크기 고정**(특정 모델 하나로 통일),
  **놓는 자세 규칙화**(예: 라벨이 카메라를 향하게 눕혀서 항상 동일하게 배치)
  - 크기 고정의 이점: 화면상 bbox 크기로 실제 거리를 역산할 수 있어(단안 카메라 거리
    추정) 접근 제어가 안정적
  - 자세 고정의 이점: 그립 시퀀스를 물체 방향에 따라 분기할 필요가 없어짐
- **대비 확보**: 탐색 구역에 바닥/책상과 대비되는 매트를 깔 수 있으면 사용(현장 통제
  가능 범위 내에서)
- 로봇은 책상 앞 정위치에 이미 있다고 가정, **바퀴 이동은 픽업 로직에 관여하지 않음**
  (팔+손목 카메라만으로 처리 — 책상 범위가 좁아 불필요)

## 아키텍처

```
사용자 음성 "약 좀 찾아서 갖다줘"
  │
  ▼
[에이보 dialogue_node]  (robot_ws 저장소, 기존)
  │ LLM tool-calling으로 의도 판단 (lekiwi_tool.py에 신규 skill 선언 추가)
  ▼
/lekiwi_command 토픽 (String)
  │
  ▼
[lekiwi_command_node.py]  (robot_ws 저장소, 기존 — 변경 불필요)
  │ SKILL_MAP(lekiwi_control.py)에 신규 항목 추가:
  │   host_param: 'laptop_ssh_host'  (기존 pick_cube 자리가 이미 이 구조로 설계돼 있었음)
  │ SSH로 노트북에서 아래 스크립트 실행
  ▼
[이 저장소] pick_pill_bottle.py  (노트북에서 실행, 신규 개발)
  │ LeKiwiClient(LeRobot ZMQ)로 LeKiwi에 연결
  │ 손목 카메라 프레임 수신 → YOLO 추론 → 접근/정렬/집기 제어
  ▼
LeKiwi (팔+그리퍼 구동)
  │
  ▼
결과(성공/실패)를 SSH stdout으로 반환
  │
  ▼
에이보가 결과에 따라 음성 응답
```

**핵심 판단**: `pick_pill_bottle.py`는 ROS2 노드가 아니라 독립 파이썬 스크립트다(LeRobot의
`LeKiwiClient`로 직접 통신, rclpy 불필요). `robot_ws`와 기술 스택이 달라(LeRobot,
ultralytics/YOLO 등 별도 의존성) 이 저장소로 완전히 분리했다 — `robot_ws`가 이미 따르는
관례(CosyVoice/DeepFilterNet 등 무거운 서브프로젝트를 별도 venv로 분리)와 일치하고,
"메인 프로그램+플러그인" 구조 원칙과도 맞는다. `robot_ws` 쪽 변경은 `lekiwi_tool.py`에
skill 선언 추가 + `lekiwi_control.py`의 `SKILL_MAP`에 항목 하나 추가뿐이다.

**사전조건**: 노트북에 SSH 서버 활성화 필요(`lekiwi_command_node`의 `laptop_ssh_host`
파라미터가 현재 비어있음, 이 작업의 확인 목록에 포함).

## 제어 알고리즘

```
1. 연결: LeKiwiClient 연결 (~8.8초 오버헤드, 2026-08-11 실측 확인됨)
2. 탐색: 손목 카메라로 YOLO 반복 추론
   - 기본 자세에서 바로 보일 것으로 기대(책상 범위가 좁음) — 안 보이면 가벼운
     스윕(팔을 좌우로 소폭 이동)으로 안전망만 마련, 복잡한 탐색 로직은 불필요
3. 접근+정렬 (폐루프):
   - bbox 중심 x좌표 오차 → 팔 좌우 미세 조정
   - bbox 크기(알고 있는 실제 물체 크기 기준 역산한 거리) → 접근 거리 계산
   - 중심 정렬 + 목표 거리 도달 시 다음 단계로
4. 하강+그립: 자세가 고정돼 있다는 전제로, 고정된 시퀀스(내려가기→그리퍼 닫기)
5. 성공 판정: 그리퍼 서보의 Present_Load/Present_Current 레지스터 값으로 판정
   (Feetech 서보에 이미 존재하는 읽기 전용 레지스터 — lerobot의
   `motors/feetech/tables.py`에 이미 정의됨, 새 하드웨어 불필요, 2026-08-12 확인)
6. 들어올리기+retract, 결과를 SSH stdout으로 반환
```

## 인식(YOLO) 계획

1. **1단계(공짜 시도)**: YOLO 사전학습 모델(COCO)의 기존 "bottle" 클래스로 우리 약통이
   인식되는지 먼저 시험. 되면 학습 단계 생략 가능
2. **2단계(안 되면 파인튜닝)**: 고정된 약통을 책상 세팅에서 다양한 거리/각도로
   150~300장 촬영(자세는 고정이므로 거리/각도 변주 위주) → 라벨링 → YOLOv8n/v11n을
   COCO 사전학습 가중치에서 파인튜닝(이 GPU 기준 학습 자체는 짧게 끝날 것으로 예상,
   미실측). 대략 하루 작업으로 예상

## 에러 처리

- 탐색 타임아웃(예: 8초) 시 실패 판정 → "못 찾았어요" 안내
- 폐루프 진행 중 목표를 놓치면(bbox 사라짐) 잠깐 유지 후 안 돌아오면 재탐색으로 복귀
- 그리퍼 "닫힘 부하 신호" 없으면(=허공을 잡음) 실패 판정, 재시도는 이번 스코프 밖
- SSH/네트워크 단절: `lekiwi_control.py`의 기존 `active_job` 동시성 락 + `ALIVE`/`DEAD`
  생존확인 패턴을 그대로 재사용(이 저장소가 아니라 `robot_ws` 쪽 기존 로직)

## 테스트/검증 계획 (배점표 "성능 및 결과 검증" 겨냥)

- 약통을 책상 위 정해진 범위 내 여러 지점(예: 5곳)에 규칙대로 배치, 각 지점 3회씩 반복
- 성공/실패 여부, 소요시간 기록 → "N/M회 성공, 평균 X초" 형태로 발표자료/영상에 제시
- 영상은 실제 반복 시행 중 성공한 테이크를 편집해 구성(좌표 하드코딩 등 결과 조작 금지)

## 폴백 플랜

2주 안에 비전+집기 파이프라인이 충분히 안정화되지 않을 경우, 라이브 시연을 **음성
명령으로 LeKiwi 이동/방향전환만 보여주는 축소판**으로 다운그레이드한다 — 이 기능은
이미 실물 검증이 끝난 상태(2026-08-10)라 100% 안전한 대체재다. 단, 이 경우 창의성/
성능검증 점수가 낮아질 것으로 예상되므로 최후 수단으로만 사용한다.

## 알려진 리스크 (완화책 포함)

| 리스크 | 완화책 |
|---|---|
| 물체 방향에 따라 그립 실패 | 놓는 자세를 규칙화해 고정 |
| 거리 추정 부정확 | 물체 실제 크기 고정값 기반 역산으로 완화 |
| 그립 성공 여부 확인 어려움 | 그리퍼 서보 Present_Load/Current 판독(신규 하드웨어 불필요) |
| 학습 환경≠실제 대회장(조명 등) | 1차→2차 사이 시간이 짧아 재학습 여유 거의 없음 — 완화책 미정, 리스크로 남김 |
